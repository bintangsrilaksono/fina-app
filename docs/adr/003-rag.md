# ADR 003: pgvector-in-Postgres for RAG, Whole-Record Embedding

**Status:** INFERRED (reconstructed from [migrations/setup-vector.sql](../../migrations/setup-vector.sql), [migrations/setup-db.sql](../../migrations/setup-db.sql), and [embedding.ts](../../src/features/ai/embedding.ts))

## Context

The app already uses Supabase Postgres for relational data (transactions) and needs semantic search over that same data for RAG-grounded chat and generative content.

## Decision (as implemented)

Enable the `pgvector` extension inside the existing Supabase Postgres instance and add a `vector(768)` column directly on the `transactions` table, rather than standing up a separate vector-database service. Embed the entire transaction record as one unit (`JSON.stringify(transaction)`) rather than embedding individual fields or chunking.

## Evidence

- No vector-DB-as-a-service dependency exists anywhere in `package.json`.
- The embedding column lives on the *same table* as the relational data it describes, and is written in the same `createTransaction`/`updateTransaction` calls (`handleEmbedding`), not a separate indexing job — confirming embeddings were designed to stay consistent with the source row by construction, not by a sync process.

## Consequences

- Zero additional infrastructure; embeddings are always consistent with the row (no separate index to fall out of sync).
- No `ivfflat`/`hnsw` index exists on the `embedding` column — acceptable at small scale (sequential scan), a scaling concern beyond it (see [11-database-and-vector-db.md](../11-database-and-vector-db.md)).
- Whole-record embedding avoids the need for a chunking strategy, appropriate for small atomic records but not a pattern to reuse for long-document RAG.
- Because embedding happens synchronously on write, a Gemini outage blocks transaction writes entirely, not just search — an availability coupling that a queue-based async-embedding design would have avoided.

## Alternatives not taken (inferred)

A dedicated vector-DB service was very likely never considered necessary given the small expected data volume (a single user's personal transactions) — a reasonable choice at this scale, revisit only if data volume or the number of tables needing vector search grows substantially.
